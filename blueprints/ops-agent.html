Blueprint #1: Autonomous Ops Agent

An agent that resolves what it can prove it should resolve, and hands the rest to a human with the work already done.

Last updated October 29, 2026.

Run the sandbox 14 scenarios, an answer key, and results computed in your browser.

Problem

Manual operations work is slow in a way that's hard to put a number on: an alert fires, someone context-switches, reads a runbook, does the obvious thing. Most incidents are boring and repetitive. Full autonomy is worse than the alternative, because the one time the agent guesses wrong on something irreversible, you've traded a slow afternoon for an incident.

So I didn't build an agent that does everything. I built one that can prove which of my incidents are safe to resolve alone.

Goal

Resolve the routine cases without a human in the loop, and for everything else, arrive at the on-call engineer with a diagnosis and a proposed remediation already prepared — without ever executing it.

How the decision actually works

The loop is deliberately small: classify, select a candidate action, clear the guardrails, then either execute or escalate. I run the guardrails after picking an action, and any one of them can stop it.

  1. Classify. Severity comes from the signals — error rate, affected users, revenue at risk — not from the alert's own label. An alert that calls itself "critical" gets treated as critical only if the numbers say so.
  2. Select. The candidate action is chosen from a fixed list of approved playbooks, matched on symptom. There is no free-form action generation, because a generated command has an unbounded blast radius.
  3. Check the guards. Confidence threshold, risk tier, blast-radius cap, runbook coverage, and a blocklist for destructive requests.
  4. Act or escalate. Every guard that fired is recorded, so an escalation isn't "the agent was unsure" — it's "the agent stopped at this line."

Guardrails

  • Low-risk only. Autonomous execution is limited to actions that are reversible. A rollback or migration never auto-runs, however clear the signal.
  • Confidence threshold. If the evidence is thin, the agent doesn't act confidently and weakly — it escalates.
  • Blast-radius cap. Past a set number of affected users or revenue at risk, a human owns the decision even if the playbook is safe.
  • Destructive-action blocklist. Delete, migration, credential rotation, billing changes: never autonomous.
  • Audit trail. Every step, every guard, every value that was checked, in order.

Testing it

The thing I care most about here is that the guardrail logic is testable. I reduced the decision layer to deterministic rules so I could stop guessing and start asserting.

I wrote 14 incidents and, for each one, what a competent on-call engineer should do — before looking at what the engine returned. That answer key is the only reason a pass rate means anything. The suite also checks that the engine replays identically, and that every guardrail is actually exercised by at least one scenario (an untriggered guard is a guard you haven't tested).

You can run it yourself: in the sandbox, or with node demo/ops-agent-engine.js from the repo root. The script exits non-zero when a scenario diverges or the replay stops being deterministic, so it can gate a change.

What that measures: decision agreement against my answer key, how often the agent acts without a human, and guardrail coverage. What it does not measure: model accuracy, latency, cost, or behaviour under real production traffic — there is no model in the tested path.

Human-in-the-Loop

High-impact actions always require explicit human approval. More usefully, when the agent escalates it hands over the diagnosis, the candidate action, the guard that stopped it, and the numbers behind it — so the human starts from a decision, not from a blank page.

Tooling

  • Orchestration: n8n — deterministic workflows I can read and version, with the agent as one node rather than the whole system.
  • Reasoning: an LLM planner for diagnosis and for writing the escalation summary. It does not choose the executed command.
  • Rules: plain code for classification and guards, because these are the parts that must be testable and identical on every run.
  • Interfaces: APIs, dashboards and notifications for the actions and the handover.

Result

I don't have a production number for this agent yet, so I'm not quoting one. The only figure I can stand behind is the test result, and you can reproduce it: the sandbox suite compares the engine against an answer key of 14 scenarios and reports decision accuracy, how often it acted without a human, and unsafe executions.

If you've seen a "90% issue resolution" figure attached to this agent, that's my fault for pairing them loosely. 90% was first-contact resolution in an IT support role at Pitason & Smart Pro in 2022 — a human resolving tickets on first contact, not this agent resolving incidents. The figure is real; the attribution was wrong, and I've corrected it everywhere it appeared.

The part I'd actually defend is quieter: every autonomous action traces back to an approved playbook and a set of guards that passed, and every escalation says exactly why.

What I'd change next

  • Feed real incident history in and grow the playbook list from evidence rather than imagination.
  • Add a shadow mode where the agent proposes decisions without executing them, so I can compare against what humans did.
  • Track how often a human overrides an escalation — the most useful signal about whether the guards are tuned right.
