Blueprint #3: Personal Productivity Agent

An agent that holds the plan with you and never sends, books, or commits anything on your behalf.

Last updated October 29, 2026.

Problem

The hard part of getting work done isn't knowing what to do. It's the cost of holding twenty open loops in your head, and the friction of starting each one. Productivity tools usually add a loop instead of closing one.

Goal

Reduce the number of things a person has to remember, without taking decisions away from them. The agent should be able to say what it thinks matters and why, and then wait.

How I designed it

  1. Intake. Tasks arrive from email, notes and chat, and get normalised into one list — so the person stops reconciling five inboxes.
  2. Priority scoring. Each task gets a score from deadlines, dependencies and stated importance. The score is shown, not hidden, because a priority you can't interrogate is a priority you won't trust.
  3. Planning. The agent proposes a sequence for the day and flags what won't fit. Proposals, never commitments.
  4. Follow-through. Reminders and nudges are the agent's job; sending the email, booking the meeting, and committing the time are not.
  5. State visibility. At any point the person can see why something was prioritised, what was deferred, and what the agent isn't sure about.

The constraint I care most about

The agent never schedules, sends, or commits on the user's behalf without explicit confirmation. Not because it can't be made reliable, but because the asymmetry is wrong: a helpful suggestion costs a glance, and an unrequested action costs trust in everything else the agent says.

Tooling

  • Planning: an LLM task planner over a normalised task graph.
  • Integration: calendar and task APIs, read-heavy by design.
  • Notifications: email, chat and mobile — the agent asks, the person decides.

Human-in-the-Loop

Confirmation is the default for anything that leaves the user's own workspace. Where the agent is unsure, it says so and offers two options rather than picking one.

Status

This one is a design write-up. I'm not quoting a productivity number for it, because I don't have a measurement I'd stand behind yet — task completion is easy to measure badly and hard to measure well.

What I'd change next

  • Define a completion metric before any pilot data is collected, not after.
  • Test whether showing the priority score actually changes what people do, or just adds noise.
