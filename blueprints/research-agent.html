Blueprint #2: Research & Reporting Agent

An agent that gathers and checks before it writes, so the report is something a human can verify rather than something they have to trust.

Last updated October 29, 2026.

Problem

Research is slow, and it's inconsistent in a specific way: the quality of the output depends on how tired the person doing it is. Ask a model to skip the reading and just produce the summary, and you get fluent text with no provenance — which is worse than slow, because it looks finished.

Goal

An agent that does the gathering and the checking at machine speed, but presents every claim with the source that supports it, and never publishes on its own.

How I built it

  1. Decompose the question. The agent turns the brief into sub-questions, so retrieval has something specific to look for.
  2. Retrieve broadly, then filter. Sources come in from search and from my indexed corpus, then get scored for credibility and recency before anything is read closely.
  3. Verify before synthesising. A claim that appears in one low-quality source doesn't become a sentence in the report. Claims need support, and the report keeps the link.
  4. Write with provenance. Every paragraph carries its citations. If a claim can't be traced, it doesn't ship.
  5. Hand over for review. A human approves the report before distribution, and can see what was rejected as well as what was used.

Where the speed came from

Most of the retrieval speed-up was structural rather than clever: chunking that matched how the documents are actually read, an index sized for the queries I really run instead of a generic default, and a filter pass that discards low-credibility sources before they get embedded into context. The model was rarely the bottleneck.

On my own retrieval pipeline, that came out to 40% faster retrieval — measured on my pipeline, with the baseline and measurement window available on request. It isn't an independently audited benchmark, and it describes retrieval only, not end-to-end report quality.

What this does not claim: better report accuracy, lower cost per report, or faster human review. Retrieval latency is one measurable slice, and I quote only that slice.

Tooling

  • Retrieval: search APIs for the open web, plus a vector store over my own corpus.
  • Reasoning: an LLM with structured prompts for decomposition, verification and drafting — each stage constrained and checkable.
  • Output: reports and summaries that keep their citations in the artefact, not in a side channel.

Human-in-the-Loop

The agent prepares; a human publishes. Reviewers see the draft, the source list, the confidence per claim, and what got dropped — because the useful review question isn't "does this read well" but "is this true".

Failure modes I design around

  • Confident synthesis of thin evidence. Mitigated by requiring support per claim rather than per report.
  • Source laundering. Five pages repeating the same weak claim are one source, not five.
  • Stale material. Recency is scored, and dates are surfaced next to the claim.

What I'd change next

  • Build a held-out claim set so verification is measured, not asserted.
  • Track reviewer edit distance as the real quality signal.
