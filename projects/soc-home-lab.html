SOC Analyst Home Lab

A practice environment I built to learn how detection actually feels: logs going in, alerts coming out, and a decision on every one of them.

  • Self-directed
  • Windows + Linux VMs
  • Splunk / Wazuh
  • Lab exercise
Run the log-triage lab A detector over a synthetic auth log, plus seven triage cases.

Why I built it

You cannot get hired into a SOC without SOC experience, and you cannot get SOC experience without a SOC. So I built a small one: a couple of virtual machines generating the kinds of logs a real environment produces, a SIEM collecting them, and enough detection content to be forced into judgement calls.

The setup

  • Virtual machines — Windows and Linux guests simulating a small mixed environment, because most real estates are a mix and the interesting events happen at the boundary.
  • SIEM — Splunk / Wazuh, configured for log collection and monitoring. The workflow is the same on either; what changes is the query language.
  • Log sources — system, authentication and security logs, which is where the cheap and loud attacks show up first.
  • Dashboards — built to visualise authentication events and alert volume, so abnormal becomes visible as a shape before it becomes a number.

What I detected

  • Failed login attempts and brute-force patterns — the same source hammering accounts, and the distinction between that and a user who has forgotten which password goes where.
  • Password spraying — many accounts, few attempts each; the pattern that per-account lockout rules never catch.
  • Suspicious scripts and abnormal behaviour — processes and sessions that do not match the machine's normal rhythm.
  • Successful login after repeated failures — the event that turns a noisy alert into an incident, and the one worth escalating immediately.

The incident response report

For a simulated attack scenario I wrote the report the way I would want to receive it: what happened, in what order, which evidence supports each step, what was affected, what I did, and what I would have needed to do it faster. Writing it was the part that taught me the most — an alert is easy to spot, a defensible narrative is not.

What this is and is not

This is a lab. It is not client work, not a production SOC, and not evidence that I have handled live incidents. What it does demonstrate is that I can stand up the tooling, write detection content, triage an alert to a decision, and document it — which is what an entry-level SOC role asks for.

What I'd do next

  • Map detections to MITRE ATT&CK techniques explicitly, so coverage gaps are visible instead of assumed.
  • Add a second log source (DNS or proxy) — authentication logs alone give a narrow view.
  • Write detection rules as code and version them, so changes can be reviewed and regressions caught.
  • Build a small answer-key test set for detection logic, the way the log-triage lab does.
