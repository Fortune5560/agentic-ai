Inventory Automation Web App

A small front-end tool for the part of stock work that is pure repetition: find the item, change the number, record who changed it.

  • HTML · CSS · JavaScript
  • Portfolio project
  • Practice build

The problem it addresses

Inventory work in a small business usually lives in a spreadsheet, a notebook, or a person's head. That works until someone is away, or until two people edit the same row and one of them silently wins. The fix is not artificial intelligence; it is a small, boring tool that refuses to accept bad input.

What it does

  • CRUD-style operations on stock records — add, view, edit, remove — with the list updating as you work.
  • Basic data handling so the current state of the list is what the screen shows, not a stale copy of it.
  • Form validation that catches empty fields, negative quantities and mismatched units before they reach the data.
  • Error handling that tells the user what went wrong in words rather than failing silently with a console message nobody sees.

How it is built

Plain HTML, CSS and JavaScript, no framework and no build step. That was a deliberate constraint: the tool has to be something a small business could open, understand and run without a toolchain, and something I could hand over without writing a manual.

The interesting work is all in the edges — what happens when a quantity field is empty, when a record is edited twice, when the browser is interrupted mid-edit. Most of the code is there to prevent the boring failures that make a tool untrustworthy.

What this demonstrates — and what it doesn't

It demonstrates: that I can build, debug and document a working front-end tool, handle validation and error states, and design for someone who is not technical.

It does not demonstrate measured business impact. This is a practice build, and no runtime number is quoted for it.

The 40% faster retrieval figure elsewhere on this site belongs to a different piece of work — digitizing the inventory database at Rom Oil (2024–2025), where the records were real and the clock was the business's. I have deliberately not attached that number to this app.

What I'd do next

  • Persist data properly — this needs storage that survives a refresh before it is useful to anyone.
  • Add an audit trail: who changed what, when. In stock work, the change history is often more valuable than the current number.
  • Write tests for the validation rules, since they are the whole point of the tool.
  • Try it on a real workflow for a week and see which field people actually get wrong.
